## Functional gaps

- **Cross-asset coverage** ([MARKET_COVERAGE.md](MARKET_COVERAGE.md)). What fills each tile now:
  - keyless: BTC/ETH live (Binance, Coinbase fallback); US2Y–US30Y Treasury daily closes with `change_bp`; the 7 FX pairs from the ECB fix (change vs the previous fix); DXY as the ECB-derived replica of the ICE formula; WTI/BRENT EIA daily spot (weekly release, 1–8 days old); GOLD through the PAXG proxy (Binance, Coinbase fallback);
  - `FRED_API_KEY`: SP500, NASDAQ and VIX daily closes (VIXCLS lags several days), WTI/BRENT fallback;
  - `FINNHUB_API_KEY`: the 10 equities (change vs previous close) and the SPY/QQQ/IWM proxies;
  - Alpaca keys: ETF proxies (SPY, QQQ, IWM, GLD, UUP, USO, BNO), the equity fallback (IEX), daily bars for technical levels, Benzinga news;
  - Massive only: RUSSELL level (otherwise the IWM proxy), live index levels, intraday FX and live commodity futures (futures methods exist but are not polled).

  A tile with nothing shows its coverage status (NOT_CONFIGURED with the missing key, NO_DATA_YET, DISABLED). Closes and proxies never reach decisions: the cross-asset component stays *missing* without FRESH quotes (never guessed), and the regime falls back on the labelled last-close basis for display only.
- **GOLD outside CME hours.** The headline is the 24/7 PAXG price; no in-session snapshot is stored yet, so there is no FRIDAY CLOSE gold level.
- **In-process loops.** The new loops (`alpaca_quotes`, `alpaca_bars`, `alpaca_news`, `eia_spot`, `treasury_yields`, and the PAXG `proxy_rest_fallback` inside `quotes`) run only in the API process (`backend/runtime.py`). They are not in Celery `POLLERS` (`backend/workers.py`), so a Celery deployment still runs them in the API.
- **BTC/ETH ticks are written on the event loop** (`handle_binance_message` → `ingest_quote`, one small commit per tick). Proxy writes already go through `asyncio.to_thread`.
- **Treasury `extra_holidays`** (`config/rules.d/market.json` `daily_closes.schedules.treasury`: bond-market holidays the NYSE keeps open) are listed through 2027 and need yearly upkeep; a missing date makes a correct close look STALE.
- **Alpaca terms.** Personal, non-commercial use, no redistribution; Alpaca content is intended for US residents (the owner was informed). IEX is a single exchange, not the consolidated tape.
- **FRED VIXCLS lags** Cboe by several days, so VIX is usually a STALE close.
- **No free macro consensus or central-bank market pricing.** Consensus comes only from FMP (`FMP_API_KEY`); Finnhub earnings estimates are labelled "Finnhub estimate", never consensus. No adapter supplies `market_pricing` or `expected_next_rate`. The event-aware dashboard shows them as NO CONSENSUS / UNKNOWN, never invented.
- **Event-aware dashboard** (`imbunatatire.md`, contract [EVENT_AWARENESS.md](EVENT_AWARENESS.md)) is implemented: `backend/event_risk.py`, the `market_interpreter` role (`backend/interpretation.py`, [AI_AGENTS.md](AI_AGENTS.md)) and the new calendar sources ([DATA_SOURCES.md](DATA_SOURCES.md)). Open items:
  - *Calendar upkeep.* UMich release dates are configured only through 2026-12-18 (`providers.json` `econ_calendars.surveys.umich.dates`); later releases are not listed and `survey_schedule` health says so. Conference Board `exceptions` is empty, so a release moved off the last Tuesday shows on the rule date. Treasury refunding rows assume the clock time of the previous release (`assume_previous_release_time`).
  - *BLS schedule.* The BLS ICS needs a contact e-mail in `SEC_USER_AGENT` and was not exercised live. Without it the FRED release-date fallback (needs `FRED_API_KEY`) gives dates with configured standard times; with neither, CPI, NFP, PPI, JOLTS and ECI appear only if FMP lists them.
  - *In-process only.* Celery has no market-interpretation task (`backend/workers.py`; its `interpretation` kind is the decision recalculation `hub.analyze`). `Runtime.start` always runs `interpretation_loop` in the API process. `observe()`, the trigger state and the calendar minimum intervals live on the `Runtime` instance, and a Celery task builds a fresh `Runtime` per task (`workers._with_hub`), so triggers seen in a worker never reach the interpretation loop and `calendar_sources.min_seconds` does not throttle Celery calendar tasks.
  - *Interpreter latency and quota.* Live runs took about 150–200 s per generation with `kimi-k3` through Ollama cloud (an operational observation; the code does not measure it). The role has a 300 s timeout (from the send) and 1 attempt (`ai_runtime.json`), so a slower generation falls to the backup model, then to the labelled deterministic summary. An HTTP 429 on chat no longer opens the provider circuit: the shared LLM limiter (`backend/llm_limiter.py`) halves its concurrency, pauses new starts and retries, and the interpreter has the highest queue priority.
  - *Ollama cloud concurrency is unknown.* The subscription's real limit on parallel chat requests is not published and was not measured. The limiter starts at `ai_runtime.limiter.max_concurrent` (4) and adapts (a 429 halves it, 5 consecutive successes add 1 after quiet times of 30 s, or 300 s before it probes again the level that got the last 429), so the configured values are a starting point, not a known quota. `ai_runs.queue_wait_ms` stores the queue wait apart from `latency_ms`, but nothing yet reports how long the extractor backlog is. The feed loop still awaits one extraction per document, so during a backlog one document can hold its feed loop for up to the extractor's 1800 s queue wait (aging bounds how long it is overtaken, not the backlog itself). An exhausted quota (a 429 with a `Retry-After` above 60 s) fails calls at once but is still probed after each capped 60 s pause; the quota's reset time is not tracked.
  - *research_planner volume.* Every post-event MARKET DIVERGENCE starts one `research_planner` call plus up to 3 web searches at search-budget priority 0 (`refresh.divergence_research`), retried every 60 s while it cannot start. Several divergences after one release compete with breaking-news corroboration for the same hourly budget and for the planner's daily cap (40 requests). Hot topics, X posts and price anomalies are limited to 2 attempts per event and one per anomaly every 6 h.
- **The Ollama cloud usage quota is unknown.** Ollama does not publish the subscription's quota or how much of it is left, and the app cannot read it. The daily AI budget (`config/rules.d/ai_runtime.json` `budget`, [AI_AGENTS.md](AI_AGENTS.md#daily-ai-budget-backendai_budgetpy)) defaults to about 400 chat requests a day (measured before: about 950 a day, 77 % from the research planner), spread with a 2-hour pace window and a 25 % reserve for the interpretation, the chief analyst and the auditor. The value is an estimate meant to last the day, not a known limit: if HTTP 429 answers still come late in the day, lower it in Settings → AI models; if the day ends with budget left, raise it. The budget counts requests, not tokens; token counts are stored (`prompt_tokens`, `completion_tokens`) and shown, but no token limit is enforced. Requests are the HTTP requests actually sent (transport and limiter retries included); a request the client gave up on (a read timeout) still counts once, although Ollama may have kept generating it. The per-role pace (`spread.role_pace`) and the caps were checked against a day simulation, not against a measured day; revisit them after a few days of `GET /api/ai/usage`. The chief analyst / auditor reuse (`decision.ai_reuse_seconds`) is kept in memory only.
- **AI roles are unassigned on a fresh database.** This is deliberate: the specification says administrators choose models. Run `.venv\Scripts\python -m scripts.check_ollama --configure-roles` or assign them in Settings → AI models. Until then no extraction, fact-check or chief/auditor calls happen, and the Ollama provider stays `PENDING`. `market_interpreter` inherits the `chief_analyst` primary and backup at the next startup after `chief_analyst` is assigned (audited `role_inherited`).
- **Semantic deduplication** uses a local lexical embedding (character n-grams), shared entities and time proximity. The pgvector column exists, but no neural embedding model is wired in, so differently worded reports of one story can stay separate.
- **Entity extraction** is a capitalisation heuristic with a stop list, not NER. Topics derived from entities (when no causal rule matches) are coarse.
- **X filtered stream** (`set_stream_rules`, `parse_stream_line`) needs an X tier that allows streaming. The recent-search polling path is used otherwise.
- **Horizontal scaling.** Only one API instance may own the exchange WebSocket ingestor. There is no leader election for several API replicas; Celery beat must also run as a single instance.
- **Calibrated probabilities** stay hidden until `min_comparable` / per-horizon minimum samples are reached (currently n=0 on a fresh database). Champion/challenger promotion is manual and audited. Nothing auto-promotes.
- **Admin config editing** in the UI covers the `refresh`, `alerts`, `scoring` and `ai_budget` fragments. Sources and roles have their own screens. Other fragments (causal graph, regime, verification, dedupe) are edited as files and hot-reloaded by content hash.
- **Briefs** are deterministic templates stored per cycle. No LLM narrative is generated.
- **Record tables** (analytics, AI runs, alerts …) store JSON payloads with an id and `created_at`. Only core tables have typed columns and SQL foreign keys. Retention exists for ticks and derived rows; Timescale compression policies are not configured.
- **Tracing.** Structured JSON logs carry request and trace ids. The OTLP exporter activates only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set and the optional `opentelemetry` packages are installed; no collector has been tested.

- **Events merged under earlier dedupe rules** (a monthly release joined to last month's, several OFSI licences in one event) stay merged in existing databases. `scripts/split_merged_events.py` (`Ingestion.split_merged_events`) re-splits them once per `dedupe_version`, audited; a dry run on a copy of the owner's data planned 31 splits (72 documents into 68 new events), all checked correct, nothing lost, idempotent. It is not run automatically: take a copy of `market_hub.db`, run it with `--dry-run`, then for real. Known limits: documents joined by the same URL are not re-checked (Benzinga sometimes gives unrelated stories the generic `/quote/<SYM>` URL), split events do not reset AI fields computed before the split, and there is no undo tool (each moved document keeps `dedupe.split_from` / `previous`).
- **Live index levels.** Without a Massive (or other entitled) index feed, S&P 500, Nasdaq and Russell show FRED daily closes (labelled) plus the SPY/QQQ/IWM ETF proxies for direction, so the regime stays on the labelled last-close basis even while US markets are open.
- **Interpretation freshness.** With the Ollama cloud quota exhausted (HTTP 429 after the limiter's retries) the AI view is the labelled deterministic summary; when it is older than its refresh interval it is marked STALE with its age.

## Known behaviours to keep in mind

- STALE events (official releases older than their verification window) show "fact confidence: not current". They do not trigger recalculation or alerts.
- Level states and level-break alerts require a clear break: at least the larger of 0.1 % of the level and 0.25 × ATR (`config/rules.d/alerts.json`).
- Coinbase is the crypto and PAXG fallback and stays `PENDING` while Binance is healthy.
- GDELT raw-batch downloads occasionally return 404 for the newest batch. The adapter retries older batches (`fallback_batches`) and recovers on the next poll.

## Performance constraints

- **Config reads.** `rules()` (`backend/config.py`) returns an independent unpickled copy of the whole merged configuration on every call (files are re-checked at most once a second). Code that runs per row, per tick or per event reads the configuration once per loop, or uses `rules_view()`: one shared object that must never be mutated (`sessions.ruleset()` and `event_risk.settings()` use it).
- **Regime correlation bars.** The display regime (dashboard, `/api/regime`, briefs, the event-risk snapshot and the interpreter) reuses the one-minute correlation bars for up to `regime.correlation_bars_cache_seconds` (15 s; `HubService.correlation_bars(reuse=True)`). Decision scoring never reuses them.
